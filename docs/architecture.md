# Architecture

## One repository, one Cargo workspace

Everything is in one repository and one Cargo workspace: the hub (`hermes-server/`), the Linux agent (`agent-linux/`), what agents share
(`pkg/agentkit`) and the gRPC contract (`proto/`, generated by `pkg/proto`). A change to the contract or a collector is one pull request
that builds and tests all of it; nothing is downloaded or versioned as a dependency, and moving the repository to another Git server changes nothing.
Hub and agents are released independently (tags `server-X.Y.Z`, `agent-linux-X.Y.Z`), so `agent.proto` has to stay backward compatible: a new hub
must accept agents that were installed earlier (only add fields and `oneof` cases; never renumber; see the rules at the top of the file).

## Layout

```
proto/infraviz/v1/agent.proto   the contract: one gRPC stream per agent
pkg/proto           generated code (tonic/prost) + JSON <-> protobuf Struct (node meta is free-form)
pkg/agentkit        Config (environment), Sink (where a collector writes), Uplink (the stream: reconnect, resync, heartbeat), run loop, Differ, netrate, host Sampler
pkg/swarm           the Docker Swarm collector for both agents: Engine (HTTP over a unix socket or a named pipe), topology (pure), container stats
agent-linux         the agent binary; cri (the container runtime socket); collectors to come
agent-windows       the agent for Windows Swarm nodes; the CPU and memory of the machine come from kernel32
hermes-server     src: model (the browser's JSON), db (SQLite), live (state + fan-out), dedupe, ingest, rules, auth, manifest,
                    api (REST + SSE), grpc (agents), app (wiring); web (HERMES, the web app); deploy; examples/replay (a fake agent)
```

A collector reads an environment and writes into a `Sink`; in an agent the sink is the uplink. The hub never reads a cluster itself (yet): every
source is an agent, which is the production path anyway (no cluster credentials on the hub, works behind NAT).

## The agent protocol

The agent opens **one** long-lived gRPC stream (`AgentService.Session`, over TLS when `HUB_URL` is `https://`) and authenticates with
`authorization: Bearer <source token>` in the metadata. Then:

```
agent -> hub   Hello   protocol, agent id, host node, version, collector
agent -> hub   Batch   events: snapshot | status | meta | metrics | report | alive   (an empty batch is a heartbeat, once a second)
hub -> agent   Resync  "send your snapshot again" (the hub has nothing of this source)
```

Only a node can see its own volumes, and only the manager describes the swarm, so an agent can also send a **contribution**: nodes only it can see, which the hub adds to the topology of the source (per host, replacing the previous one, surviving a new snapshot of the manager).

`Hello.protocol` is the wire contract version (`hermes_proto::PROTOCOL`), not the agent's own build version. An older agent is still accepted — new
fields are additive, `pkg/proto/tests/compat.rs` pins that — but the admin sees a "protocol vechi" warning on its source card (`AgentView.protocol_outdated`) as a nudge to upgrade it, never a rejection.

The agent keeps its last snapshot current with every status and meta change, so after a reconnect (a hub restart, a dropped connection) it sends what is
true now. A stream that is silent for 20 s makes the source "down", which raises an alert. A source that is deleted while its agent is connected loses
the stream within 30 s. The hub asks for a snapshot once, not on every batch while it is on its way. Because it is a stream, the hub can later
push commands to the agent (for example an agent upgrade) on the same connection.

Because the browser cannot speak gRPC, the hub also serves REST and Server-Sent Events, on the same port. By default that port speaks plain HTTP/2
(h2c), so a reverse proxy (Traefik, nginx, ...) can terminate TLS in front of it — or the hub can terminate TLS itself, with `HUB_TLS_CERT`/`HUB_TLS_KEY`
(rustls, `axum-server`): same one port, same REST/SSE/gRPC mix, now behind real TLS with no proxy needed. `main.rs` picks between the two listeners at
startup; nothing else in the hub knows which one is in use (`AppState.settings.tls_enabled` only affects whether the session cookie sets `Secure`
without relying on an `X-Forwarded-Proto` header from a proxy that is not there).

## Networks

A `network` node is a way to reach workloads: a Docker overlay/macvlan network, or in Kubernetes a Service, an Ingress, a load balancer, and "outside" (`meta.netKind` says which). The Kubernetes collector reads Services, EndpointSlices and Ingresses (best effort: an agent whose account cannot list them draws everything else) and joins outside → Ingress → Service → pods. It belongs to the cluster, not to a host, and is joined to what is on it by `route` edges: a path exists, with no measured rate (the API does not tell who sent what; that is the flow agent, see TODO). The Swarm collector draws the networks you defined (swarm scope, not the routing mesh, with at least one task on them); `bridge`, `host`, `none` and `docker_gwbridge` are per-node plumbing and are left out.

## Flows (who talks to whom)

The node agent (one pod per node, root with no capabilities), when the source was added with "Show who talks to whom" (`FLOWS=1`, and then `hostNetwork`: the node's own network namespace), also reads the kernel's connection table and sends `Flows`: for each pair of addresses and port, the Mbit/s in each direction, and which address answered when the connection was translated (a Service address answered by a pod). The hub knows what the addresses are (`podIP` of a pod, `ip` of a Service or a node) and puts the rate on the route link that already exists: a Service to the pod that answered, outside to a load balancer or node port. A flow that matches no link is left out, never invented; the same connection seen by two nodes is counted once; rates from an agent that stopped reporting are zeroed after 20 s. The kernel only counts bytes when `net.netfilter.nf_conntrack_acct=1`.

Ingress traffic is deduced: what the pods of an ingress controller (recognised by image and labels: Traefik, ingress-nginx, HAProxy, Contour, Kong, Emissary; the agent marks them `ingressController`) exchange with the pods behind a Service that an Ingress sends to is put on that Ingress, and the same amount on the link from outside to it. The map marks these rates with `≈`. The busiest connections of a source, grouped by pair, go to the browser as the `flows` event and are listed on the wallboard; that list is also where pod-to-pod and caller-to-Service traffic shows, since the map draws no link for them.

**Limits.** Kubernetes only, and only what the node's connection table holds: with Cilium's eBPF replacement of kube-proxy the connections are not in it, Windows nodes have no such table, and a full table (`nf_conntrack_max`) loses entries. Docker Swarm cannot be done this way (who talks to whom): the traffic between containers runs through the overlay networks' own namespaces and the node's table only holds the VXLAN tunnels between nodes. What Swarm does have is the traffic of each task on its network: the engine counts bytes per interface of a container, a task on a single network (not counting `ingress`) has it on `eth0`, and the rate goes on the link from the network to the task. With more than one network on a container the interfaces do not say which is which, and no rate is claimed. An ingress controller that is not recognised puts nothing on its Ingress.

## One cluster, one source

A cluster is identified by a UID its collector reports (Kubernetes: the UID of the `kube-system` namespace), not by its name.
`dedupe` sits in front of the live state: the first source to show a cluster keeps it, and any later source for the same
cluster gets the state `duplicate` (shown in Admin → Sources, no outage alert) and draws nothing. After a restart the
source that was added first wins, whichever reconnects first. Remove the duplicate source to clear it.

## Hub → browser

`GET /api/stream` is Server-Sent Events. Every connection starts with a `snapshot`, then `status`, `meta`, `metrics`,
`alert`, `settings` and `sources` events. A browser that falls 64 events behind is dropped; its `EventSource` reconnects and gets a fresh snapshot.
Persistent state (settings, sources, alert history, heartbeats, users, sessions) lives in SQLite; the topology lives in memory and comes back when the
agents reconnect. A source the hub already knew (from SQLite) but has heard nothing from for 30 s after startup gets a placeholder `cluster` node,
`stale: true`, instead of vanishing from the map until its agent reconnects (`IStore::ensure_placeholder`).

## Login

The first visit creates the admin (argon2id hash in SQLite, PHC string format). Browsers get an HttpOnly, SameSite=Strict session cookie (Secure behind an
https proxy, or when the hub terminates TLS itself); only a
SHA-256 of the token is stored. State changing requests need the header `X-Requested-With: infraviz` (CSRF), logins are rate limited. Read-only data
(wallboard) is open to anyone only while "view without login" is on; everything that changes state or shows source details needs a
session. Agents are not users: they authenticate with their source token.

## Adding a collector

1. A module in the agent crate that runs where it can see the environment (`cri.rs` is the smallest example): `async fn run(source_id, ..., sink: SharedSink) -> anyhow::Result<()>`.
2. Call it from the `main()` of the agent through `hermes_agentkit::run`, which restarts it after ten seconds when it fails.
3. Emit nodes with ids prefixed by the source id; use `Own` = `ok|warn|crit`. New facts on the wire are new fields or `oneof` cases in `agent.proto`.

## HERMES, the web app

React + TypeScript (strict), built with Vite into static files that the hub serves. The layers depend downwards only:

```
domain/    pure logic, no React, no I/O: the model, the effective status of a node (derive), selectors, the reducer that turns an event into a new
           state, the layout of the map and the router of its links. This is where a mistake would lie about the infrastructure, so it has the tests.
hub/       the boundary to the server as small interfaces (AuthApi, SourcesApi, AlertsApi, ..., EventFeed) and one implementation over HTTP + SSE
state/     HubStore: one immutable HubState, changed only through the reducer; it talks to the hub through the interfaces; React reads it with useHubState
ui/        presentational pieces: they take props and draw
features/  the screens: tv, admin (its pages are a list in adminPages.ts), topology (the map), auth, landing
generated/ the TypeScript types, written from the Rust model by ts-rs while `cargo test` runs; CI fails when they are not what is committed
```

The SOLID rules show in the code: the store and the screens depend on the `HubClient` interfaces, never on `fetch` (the tests hand them a fake hub in memory); a new admin page or a
new provider is one entry in a list; each interface is what one part of the app needs and no more.
